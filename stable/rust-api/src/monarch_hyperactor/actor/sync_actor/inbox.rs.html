9//! Blocking handoff from a Rust actor running on Tokio to a Python driver with
10//! no persistent actor event loop.
11//!
12//! `PythonActor` owns the message and control senders.
13//! `Handler<PythonMessage>` enqueues `PendingMessage`, `Handler<MeshFailure>`
14//! enqueues `PendingSupervision`, undeliverable-message handling enqueues
15//! `PendingUndeliverable`, and sync cleanup enqueues `PendingSyncCleanup`.
16//! `Actor::init` passes the [`Receiver`] to `_sync_dispatch_loop` on
17//! the Python driver thread, which receives and runs one item at a time.
18//!
19//! # Sync-inbox invariants
20//!
21//! - **SI-1 (two planes, one consumer):** message and control queues are each
22//!   FIFO and have one consumer. When selecting the next item, control has
23//!   priority over messages; it never preempts an item already running.
24//! - **SI-2 (enqueue before wake):** a sender enqueues its value before writing
25//!   the common wake pipe. A wake byte carries no queue or item identity and
26//!   may be stale.
27//! - **SI-3 (no lost wake):** after finding both queues empty, `next()` releases
28//!   the GIL and polls the pipe. Any later send has already written the pipe;
29//!   after waking, `next()` drains it and checks both queues again.
30//! - **SI-4 (GIL boundary):** Tokio enqueues `PendingMessage`,
31//!   `PendingSupervision`, `PendingUndeliverable`, and `PendingSyncCleanup`
32//!   without the GIL. The driver holds the GIL while converting them to Python
33//!   objects and releases it only while polling.
34//! - **SI-5 (disconnect):** a sender's queue disconnects before its pipe
35//!   writer closes (field order in `pympsc::Sender`), and closing the final
36//!   writer wakes a blocked receiver. A disconnected control plane means the
37//!   owning actor is gone: `next()` returns `None` without taking another
38//!   message, after any control item queued before the close.
39//! - **SI-6 (stop claim):** cleanup sets `stopping` before enqueueing
40//!   `PendingSyncCleanup`. A dequeued `QueuedSupervision` or
41//!   `QueuedUndeliverable` runs only if the driver observes `stopping` as
42//!   false. The resulting `SyncCleanup` runs if the driver is still running
43//!   and can convert it.

75/// The complete inbox created for one sync actor.
76pub(in super::super) struct Inbox {
77    /// Enqueues messages for the driver.
78    pub(in super::super) message_sender: Sender,
79    /// Enqueues `PendingSupervision`, `PendingUndeliverable`, and
80    /// `PendingSyncCleanup` for the driver.
81    pub(in super::super) control_sender: Sender,
82    /// Receives both queues, with control taking priority over messages.
83    pub(in super::super) receiver: Receiver,
84}
85
86/// Create a sync actor inbox. Both senders write the same wake pipe, so one
87/// blocking wait observes both queues.
88pub(in super::super) fn new() -> Result<Inbox, nix::Error> {
89    // SI-1 message plane: actor messages in FIFO order.
90    let (messages_tx, messages_rx) = mpsc::channel();
91
92    // SI-1 control plane: PendingSupervision, PendingUndeliverable, and
93    // PendingSyncCleanup values in FIFO order. The receiver checks this queue
94    // before the message plane.
95    let (control_tx, control_rx) = mpsc::channel();
96
97    // SI-2 common waker: the pipe carries no work or queue identity. Both
98    // pympsc::Senders enqueue first, then write through this shared Waker.
99    let (waker, read_fd) = pywaker::pipe()?;
100    let waker = Arc::new(waker);
101
102    // Inbox: both producer sides plus the single driver-owned receiver.
103    Ok(Inbox {
104        message_sender: Sender::new(messages_tx, waker.clone()),
105        control_sender: Sender::new(control_tx, waker),
106        receiver: Receiver {
107            control: Mutex::new(control_rx),
108            messages: Mutex::new(messages_rx),
109            read_fd,
110            stopping: Arc::new(AtomicBool::new(false)),
111        },
112    })
113}

115/// Blocking receiver used by one sync actor's Python driver thread.
116///
117/// Messages and control items use separate FIFO queues. Their senders share a
118/// non-blocking pipe and write one byte after enqueueing; the byte carries no
119/// work or identity and may be stale. It only tells the driver to inspect the
120/// queues again.
121///
122/// On each `_sync_dispatch_loop` iteration, the Python driver calls
123/// [`Receiver::next`] with the GIL held. `next` checks control first
124/// and then messages, converts one available item, and returns it to the driver.
125/// If both queues are empty, that same call releases the GIL and blocks in
126/// `poll()`. A pipe wake makes it reacquire the GIL and check both queues again;
127/// a stale wake may send it back to `poll()`. After `next` returns, the driver
128/// processes the item and begins its next iteration.
129///
130/// A control item cannot interrupt an item already running. After that item
131/// finishes, the next `next()` call selects queued control before queued
132/// messages. Once the control queue is disconnected, the owning actor is gone,
133/// so `next` returns `None` without taking another message. Closing the final
134/// pipe writer wakes a blocked `next`, so disconnect cannot be missed.
135///
136/// `pympsc::Sender::send` boxes each value as `Box<dyn IntoPyObjectBox>` before
137/// enqueueing it. When `next` dequeues a value, it invokes that erased
138/// conversion: `PendingMessage` becomes `QueuedMessage`, `PendingSupervision`
139/// becomes `QueuedSupervision`, `PendingUndeliverable` becomes
140/// `QueuedUndeliverable`, and `PendingSyncCleanup` becomes `SyncCleanup`. Both
141/// senders therefore stay GIL-free, and conversion happens on the driver
142/// thread.
143///
144/// Actor cleanup sets `stopping` before enqueueing `PendingSyncCleanup`. If
145/// `next` returns an older `QueuedSupervision` or `QueuedUndeliverable` first,
146/// the driver reads this flag and drops that callback instead of invoking user
147/// code. The resulting `SyncCleanup` runs if the driver is still running. The
148/// Python driver is the only
149/// consumer of the control and message queues.
150///
151/// `mpsc::Receiver` is `Send` but not `Sync`. `next` holds a shared reference
152/// to this object across [`Python::detach`], which releases the GIL while the
153/// driver waits. Wrapping each receiver in a `Mutex` makes the enclosing
154/// `Receiver` safe across that boundary. The mutexes do not represent
155/// multiple consumers and are uncontended in production.
156///
157/// `Actor::init` starts a Python `threading.Thread` whose target is
158/// `_sync_dispatch_loop`, passing this receiver as the function's `inbox`
159/// argument. The driver calls `next()` and `stopping()` on it directly; the
160/// class is an internal Rust/Python boundary, not a user API.
161#[pyclass(
162    name = "SyncInbox",
163    module = "monarch._rust_bindings.monarch_hyperactor.actor"
164)]
165pub(in super::super) struct Receiver {
166    /// Receives `PendingSupervision`, `PendingUndeliverable`, and
167    /// `PendingSyncCleanup` values sent through `pympsc::Sender::send`, which
168    /// erases each value to `Box<dyn IntoPyObjectBox>` before enqueueing it.
169    /// Checked before messages.
170    control: Mutex<mpsc::Receiver<Box<dyn IntoPyObjectBox>>>,
171    /// Receives `PendingMessage` values sent through `pympsc::Sender::send`,
172    /// which erases each value to `Box<dyn IntoPyObjectBox>` before enqueueing
173    /// it, even though this queue has one logical payload type.
174    messages: Mutex<mpsc::Receiver<Box<dyn IntoPyObjectBox>>>,
175    /// Read end of the shared wake pipe. `Inbox::message_sender` and
176    /// `Inbox::control_sender` are `pympsc::Sender`s: each owns a different
177    /// `mpsc::Sender<Box<dyn IntoPyObjectBox>>`, and both hold a clone of the
178    /// same `Arc<pywaker::Waker>`. That shared `Waker` owns the write end.
179    read_fd: OwnedFd,
180    /// Set when cleanup begins, before its control item is enqueued.
181    stopping: Arc<AtomicBool>,
182}
183
184// `next` borrows the receiver across `Python::detach`; keep that boundary
185// compiler-checked as the representation changes.
186const _: fn() = {
187    fn assert_send_sync<T: Send + Sync>() {}
188    assert_send_sync::<Receiver>
189};

197/// Result of checking one inbox plane without blocking.
198enum Take {
199    /// One queued value, removed from the plane.
200    Item(Box<dyn IntoPyObjectBox>),
201    /// No value is available, but a sender may still enqueue one.
202    Empty,
203    /// No value remains and every sender for this plane is disconnected.
204    Closed,
205}
206
207/// Check one inbox plane without blocking, consuming at most one value.
208/// The receiver lock is released before that value is converted into Python.
209fn try_take(rx: &Mutex<mpsc::Receiver<Box<dyn IntoPyObjectBox>>>) -> Take {
210    match rx
211        .lock()
212        .expect("sync inbox receiver lock should not be poisoned: only the driver takes it")
213        .try_recv()
214    {
215        Ok(item) => Take::Item(item),
216        Err(mpsc::TryRecvError::Empty) => Take::Empty,
217        Err(mpsc::TryRecvError::Disconnected) => Take::Closed,
218    }
219}
220
221impl Receiver {
222    /// The SI-6 flag cleanup sets before enqueueing `PendingSyncCleanup`.
223    pub(crate) fn stop_flag(&self) -> Arc<AtomicBool> {
224        self.stopping.clone()
225    }
226
227    /// Block until the pipe is readable, then drain it (SI-3, SI-5). A send may
228    /// occur after `next` checks both queues but before this method enters
229    /// `poll()`. That send enqueues its value before writing the pipe, so the
230    /// byte is already waiting and `poll()` returns immediately instead of
231    /// missing the wake. Closing every write end also makes the pipe readable.
232    fn wait(&self) -> nix::Result<()> {
233        // `poll` accepts a slice, so use a one-entry array and wait indefinitely
234        // for data or pipe closure.
235        let mut wake_fd = [PollFd::new(self.read_fd.as_fd(), PollFlags::POLLIN)];
236        // EINTR means a signal interrupted the wait, not that the pipe failed, so
237        // retry it.
238        retry_eintr(|| poll(&mut wake_fd, PollTimeout::NONE))?;
239
240        // Drain all wake bytes currently in the pipe. After the last byte, the
241        // non-blocking read returns EAGAIN instead of waiting for a future wake.
242        // The receiver ignores the byte values and count; pipe readability
243        // alone tells it to inspect the queues. Each read removes up to 64
244        // accumulated wake bytes.
245        let mut buf = [0u8; 64];
246        loop {
247            // Retry if a signal interrupts the read.
248            match retry_eintr(|| read(&self.read_fd, &mut buf)) {
249                // EOF: every Sender has released the pipe's write end.
250                Ok(0) => return Ok(()),
251                // One batch drained; keep reading until the pipe is empty.
252                Ok(_) => {}
253                // The non-blocking pipe is now empty.
254                Err(Errno::EAGAIN) => return Ok(()),
255                // A real pipe failure propagates through `next` to the driver.
256                Err(err) => return Err(err),
257            }
258        }
259    }
260}

262#[pymethods]
263impl Receiver {
264    /// Return one queued item, preferring control over messages (SI-1). Return
265    /// `None` once the control queue is disconnected and drained, without
266    /// taking another message (SI-5). While no item is ready and control is
267    /// still connected, call `self.wait()` with the GIL released to block on
268    /// and drain the shared wake pipe, then reacquire the GIL and recheck both
269    /// queues (SI-3, SI-4).
270    fn next(&self, py: Python<'_>) -> PyResult<Option<Py<PyAny>>> {
271        loop {
272            // SI-1: a ready control item wins without inspecting the message
273            // plane. Conversion happens after `try_take` releases its lock.
274            match try_take(&self.control) {
275                Take::Item(item) => return item.into_py_object(py).map(Some),
276                // SI-5: the owning actor is gone, so queued messages have no
277                // one to answer to.
278                Take::Closed => return Ok(None),
279                Take::Empty => {}
280            }
281            match try_take(&self.messages) {
282                // Return exactly one message, converted under the GIL.
283                Take::Item(item) => return item.into_py_object(py).map(Some),
284                // Nothing is ready and control is still connected. Release the
285                // GIL while waiting, then retry the priority checks in this
286                // same call (SI-3, SI-4).
287                Take::Empty | Take::Closed => py.detach(|| self.wait()).map_pyerr()?,
288            }
289        }
290    }
291
292    /// Whether the actor's cleanup has begun. The driver claims a callback it
293    /// has dequeued only if this is still false.
294    fn stopping(&self) -> bool {
295        self.stopping.load(Ordering::Acquire)
296    }
297}

362    /// Receive and extract the integer payload used by these tests. The caller
363    /// supplies the GIL token so tests can coordinate another thread against
364    /// the GIL release inside `next`.
365    fn next_value_with_gil(receiver: &Receiver, py: Python<'_>) -> Option<i64> {
366        receiver
367            .next(py)
368            .expect("next should not fail")
369            .map(|item| item.extract::<i64>(py).expect("items are ints"))
370    }

372    /// Receive through the production GIL and Python-conversion path.
373    fn next_value(receiver: &Receiver) -> Option<i64> {
374        monarch_with_gil_blocking(GilSite::Test, |py| next_value_with_gil(receiver, py))
375    }

400        let (received, sender) = monarch_with_gil_blocking(GilSite::Test, |py| {

403                // `next` kept it while blocked, this thread could never reach
