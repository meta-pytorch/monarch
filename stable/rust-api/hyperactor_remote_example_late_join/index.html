Connect a new client to a trainer that is already running.

This program has two roles, run in separate processes:

  • trainer runs a simulated training loop as an ordinary Tokio task, not an actor. Monarch does not start or supervise that loop. Each step updates a step count and loss using the current learning rate.
  • client connects later, reads the trainer’s state, changes its learning rate, reads the state again, and exits. The trainer keeps running.

The trainer embeds a Monarch proc containing three actors:

  • ProbeHost is the root actor. It creates the other two actors, writes the token file, and handles their supervision events.
  • Probe is a child of ProbeHost. It shares the loop’s live TrainerState behind a mutex and answers clients’ state queries and learning-rate changes. It is called a probe because clients can use it to peer into the running trainer.
  • The rendezvous actor is another child of ProbeHost, created by token::create(). It handles join requests and gives clients a reference to Probe; it does not answer the training-state requests itself.

The training loop is not a fourth actor. It remains an ordinary Tokio task, separate from this supervision tree. Clients do not own the loop or become its controller.

The client also embeds a Monarch proc. proc.client("client") creates a lightweight actor instance with its own actor address and mailbox, but no actor message loop like Probe has. Ordinary Rust code sends requests and awaits replies through ports belonging to this client instance.

To let a client find the probe, the trainer writes a token to a file. The token string contains a reference to the rendezvous actor. The client reads and parses the token, then uses that reference to send a join request to the rendezvous actor. The request carries the client’s actor address and a reply port; the client does not send the token itself.

The rendezvous actor handles the request by sending the client’s actor address to ProbeHost as a join notification, then sending a typed reference to Probe to the client’s reply port. ProbeHost logs the notification. The client then sends Snapshot and SetLearningRate requests directly to Probe, not through the rendezvous actor.

This example chooses to give the trainer the client’s actor address so ProbeHost can log who connected. The token mechanism does not require an actor address: other tokens can exchange other serializable values. Giving the trainer this address does not make the trainer send requests to the client or start supervising it.

ProbeHost handles child supervision events rather than letting them fail the root actor and terminate the trainer process. Joining establishes contact, not remote supervision: clients can come and go independently. Multiple clients can use the token, but it stops working when its creator stops.

The roles can run on the same machine or on separate hosts. This example uses plaintext TCP, which is fine on one machine or within one datacenter; between hosts in different regions or datacenters, use an encrypted transport such as ChannelTransport::MetaTls(TlsMode::Hostname) instead. Each proc listens on a non-loopback TCP address resolved from its machine’s hostname. Each hostname must resolve to such an address, and the two hosts must be able to reach each other’s listeners: requests travel to the trainer, and replies travel back to the client. Copy the trainer’s token file to the client host, or place it on a shared filesystem, before starting the client.

It demonstrates late attachment, not authentication or a Python API.
