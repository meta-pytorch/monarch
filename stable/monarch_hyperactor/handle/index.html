Handle: an observe-only handle to a background operation.

A Handle observes one operation through a shared [Core]. The operation’s producer supplies a Python outcome or a successful reply still pickled, and every observer reads it: synchronously via get(), on an asyncio loop via as_asyncio()/await, or without blocking via poll(). A published result stays observable by any number of later observers.

Most producers start when their Handle is created. A deferred producer, a stream item’s or a port receive’s, starts on the Handle’s first observation (HDL-24).

§Handle invariants (HDL-*)

Code that relies on or enforces an invariant is tagged // HDL-N, and each #[cfg(test)] test that attests one names it; read the matching entry below before changing a tagged site.

  • HDL-1 (single terminal state). A core moves from Unstarted, Running or Raw to Done or Lost once and never leaves it. Publication consumes the Publisher; only the owner of a raw reconstruction claim may finish Raw.
  • HDL-2 (outcome encoding). Done(Ok(_)) is success, Done(Err(_)) a producer/reconstruction error, and Lost producer loss (HDL-10). Raw bytes are not a completed Python outcome or successful readiness.
  • HDL-3 (non-consuming reads). No read moves the outcome out. Under the state lock an observer clones only the outcome’s Arc; after unlocking it clones the value or error (clone_ref), or, on wait_completion’s success path, reads just the Ok/Err tag. Any number of observers see the same result. Raw replies are reconstructed once before ordinary shared reads (HDL-27).
  • HDL-4 (drop does not cancel; drop never panics). Dropping a Handle never cancels a running producer; a Handle observes, it does not own the producer’s lifecycle. Producers hold the core weakly and publish through it. An unstarted deferred producer is dropped with the last observer, never polled. A producer with ObserverLoss::Stop (a port receive) instead stops when the last observer drops (HDL-23).
  • HDL-5 (GIL discipline). No Python object is touched without the GIL, and every acquisition goes through monarch_with_gil{,_blocking}. Enforced by the crate’s #![deny(clippy::disallowed_methods)] ban on raw Python::with_gil/attach – a hard compile error, not a debug_assert.
  • HDL-6 (WouldBlockRuntime is get()’s alone among the observers). Of the Handle observers only get() raises it, and only in a Tokio runtime context; as_asyncio()/__await__ off a loop raise the native RuntimeError instead. The exception type itself is not private to this module: it marks synchronous APIs that refuse to enter or block on Tokio from an existing Tokio runtime context. The Python layer also raises it for fresh root-client bootstrap (monarch._src.actor.actor_mesh), the blocking worker-loop wrappers (monarch._src.actor.bootstrap), and a returns_future .get() that would block a running event loop (monarch._src.actor.returns_future, RF-7).
  • HDL-7 (as_asyncio publish). The observer waits through wait_terminal, which checks the state before it registers a wake (HDL-25). The result is published on the loop thread through complete_asyncio_future, by the wake reader (HDL-17) or by the fallback’s call_soon_threadsafe callback (HDL-21), or, for a Handle already complete, by as_asyncio itself (HDL-22). It sets a result only on a non-cancelled future, swallowing InvalidStateError; any StopIteration (including subclasses) is wrapped in RuntimeError first, since set_exception rejects StopIteration (PEP 479). If the loop has closed, the fallback logs rather than panics and the wake reader never runs. A wake-reader failure, including a future whose done() raises, is reported through the future’s loop exception handler, as asyncio reports an exception from a callback.
  • HDL-8 (get() loop-warning is call-pattern, not outcome). get() on a running asyncio loop warns regardless of whether the value is ready: it flags the blocking-call-from-a-loop anti-pattern, not whether this call happens to block. A ready value returns after warning; under a warnings-as-errors filter the warning escalates to an error. The check uses asyncio._get_running_loop(), which returns None off a loop where asyncio.get_running_loop() builds and raises an exception.
  • HDL-9 (state lock discipline). The state lock is a leaf: while it is held, no code runs Python, acquires or releases the GIL, awaits, notifies, or drops a Python object. Lock order is GIL, then state lock. An observer clones an Arc under the lock and reads the value after unlocking, because PyErr::clone_ref can release and reacquire the GIL while it normalizes a lazy error. A transition moves the retired state out under the lock and drops it after unlocking, because dropping a Py on an attached thread can run a finalizer that re-enters the Handle. Enforced by construction; exercised by the lazy-error and re-entrant-destruction tests.
  • HDL-10 (dropped producer surfaces, never hangs). A Publisher dropped without publishing publishes Lost: a task dropped at runtime shutdown, before or after its first poll, an inline drive that unwinds, or a _HandleCompleter dropped unresolved. Every observer, on the non-blocking (poll), sync (get/wait_future), async (as_asyncio) and wait_completion paths, then receives the same producer-lifecycle failure, RuntimeError("Handle producer ended without publishing a result"), rather than waiting forever.
  • HDL-11 (Python construction is paired). Neither Handle nor _HandleCompleter has #[new]. Internal Python may call the private _new_handle_pair(), which atomically creates a pending Handle and its sole producer. The factory initializes the completer with Some(publisher). set_exception() rejects a non-BaseException before taking it; the first set_result() or valid set_exception() takes it, producing the only state transition to None, and any later completion attempt raises. Dropping the completer unresolved publishes Lost (HDL-10). Python therefore cannot create a pending Handle without its producer. Native producers remain the default; this private pair is reserved for operations whose semantics and scheduling are owned by Python.
  • HDL-12 (get() timeout contract). get() validates the timeout up front (rejecting negative/NaN/non-finite as ValueError via try_from_secs_f64, never panicking) and before the ready fast path, so an invalid timeout raises deterministically even for a ready handle. A timeout is non-cancelling: it raises TimeoutError while leaving the producer and every observer untouched, so a later poll()/get()/await still observes completion. A get() that was driving its producer hands it to Tokio first (HDL-24). The timeout bounds waiting for arrival or another reconstructor, not synchronous Python unpickling performed by this observer.
  • HDL-13 (direct Rust producer). A Rust caller can eagerly produce a Handle from a Send + 'static future. PyHandle::spawn wraps the future with conversion of a successful Rust value to Py<PyAny> under monarch_with_gil and delegates to PyHandle::spawn_pyobject. The latter starts one producer and publishes its Python value or error once through its Publisher, without a result-conversion GIL acquisition (HDL-1/HDL-2). A Publisher whose observers have all gone logs an error result instead, with the producer’s own copy of the creation traceback when one was captured. Dropping the Handle does not cancel the producer (HDL-4). call(), call_one() and choose() use PyHandle::spawn_raw, which retains the supplied creation traceback, publishes successful bytes and leaves reconstruction to an observer; errors keep the same logging path. PyHandle::wait_completion is the matching observer: it projects the terminal value to PyResult<()>, touching neither the GIL nor the Python value on the decoded success path (a tag-only read, HDL-3) and cloning the error after unlocking only on the error path (HDL-9). These are Rust-only methods outside #[pymethods] (HDL-11).
  • HDL-14 (Rust value observation is owned and non-consuming). PyHandle::wait_future returns a Send + 'static future that owns a strong reference to the core. The waiter borrows nothing from the PyHandle, survives the wrapper being dropped, and leaves the terminal value available to every other observer.
  • HDL-15 (Rust ready construction starts no work). PyHandle::from_value constructs a core already Done, with no producer and no wake. It is public to Rust callers but remains outside #[pymethods], preserving HDL-11’s direct-construction restriction.
  • HDL-16 (permanent Python identity). Handle and WouldBlockRuntime have the canonical module monarch._rust_bindings.monarch_hyperactor.handle.
  • HDL-17 (GIL-free completion wake). For a Handle still pending when as_asyncio is called, on a loop that accepts add_reader, the observer task holds a Notifier (a token, an mpsc sender and an Arc<Waker>) and the wait_terminal future. It reconstructs Raw on its worker before publishing a token. Already-decoded outcomes need no GIL in the waiter. It pushes the token and writes the loop’s pipe; the loop thread reads the value from the Handle and sets it (see crate::handle_wake). Enforced by construction: Notifier has no Py<_>, and a token follows Done or Lost, never raw arrival or claim release.
  • HDL-18 (notification ordering under supported pipe outcomes). A notifier pushes its token before writing the pipe, and the reader drains the pipe before the queue, never returning between the two; both retry EINTR. A write that succeeds or returns EAGAIN leaves a byte pending, so a token pushed after a queue drain is delivered by a later wake. EPIPE or a disconnected queue means the channel is gone and the token is dropped. Any other errno is logged as a broken wake channel, not claimed as delivered.
  • HDL-19 (loop not retained). The wake registry holds each loop as a weak key and its channel through a weak reference; the loop’s selector, through the channel’s reader callback, is the channel’s only strong owner. A channel holds no reference to its loop. It holds each pending await’s asyncio future strongly until delivery, cancellation or loop close, because asyncio holds tasks weakly and that reference is the waiting task’s only owner outside the task’s own cycle; __traverse__ exposes each entry’s future and Handle object to the garbage collector. Closing a loop therefore releases the channel-owned graph (the channel, its read end, its entries, their futures and Handles). The write end stays open until every Notifier is dropped, so a loop closed while an await waits on a Handle that never completes keeps that descriptor (HDL-20). A loop dropped without being closed while an await on a pending Handle is registered is still freed by the collector. Not freed: a loop dropped without being closed while an undelivered entry’s Handle value references it, and any independent cycle through a Handle, such as a value that references its own Handle. Both run through PyHandle, which the garbage collector does not traverse.
  • HDL-20 (late wake is harmless). A notify after its channel is gone is dropped without error or panic: the send fails, or the write gets EPIPE. This requires SIGPIPE to be ignored, as Rust’s runtime and CPython set it by default; in a process that restores SIG_DFL, a completion that races loop teardown can kill the process. Every Notifier owns the write end through its Arc<Waker> until its Handle completes, so no write reaches a reused descriptor.
  • HDL-21 (fallback). For a Handle still pending, a loop whose add_reader raises NotImplementedError or that cannot be weakly referenced uses the call_soon_threadsafe path; HDL-7 applies there unchanged.
  • HDL-22 (ready shortcut). as_asyncio() on a Handle that already holds its outcome, a value, a stored exception or producer loss (HDL-10), returns a loop future already completed with it through complete_asyncio_future, with no observer task and no wake-channel registration. Awaiting it returns without giving the loop a turn, as for any finished asyncio future. An unclaimed Raw reply is reconstructed on the loop thread first; a claimed reply follows the pending wake path without blocking that thread.
  • HDL-23 (stop when nobody can observe the result). A Handle, its clones, a blocked get(), a Rust waiter and the native waiter behind await/as_asyncio() each hold the core strongly; producers hold it weakly. When the last strong reference drops, the core’s Drop stops a producer with ObserverLoss::Stop (a port receive). Its stop future is created before its task is scheduled, so a loss before the first poll still stops it. The stop is not immediate: the task must notice it, and it can still take a message before then. Other producers keep running when their observers are dropped (HDL-4), and so does an unpickling retry after an interrupted decode (HDL-26), whose message is already taken.
  • HDL-24 (deferred start). A deferred producer starts on the first observation that passes its own checks. get() refuses on Tokio, validates its timeout and warns on a running loop before it touches the state, and as_asyncio() checks for a running loop first, so a rejected observation starts nothing. Start authority lives in the core, so any observer can start the producer, including a clone. get() drives the producer inline, on the calling thread with the GIL released; every other observation spawns it on Tokio. If Ctrl-C (on Python’s main thread) or the timeout ends a driving get() first, it hands the unfinished producer to Tokio before it raises, so the producer’s result still reaches the core and stays readable. Ctrl-C during decoding is HDL-26’s case.
  • HDL-25 (on-demand wake). A core creates its wake only when an observer must wait. A waiter clones the wake and creates its OwnedNotified under the state lock; a publisher moves the wake out under the lock and calls notify_waiters() after unlocking. Tokio delivers notify_waiters() to every OwnedNotified created before the call, polled or not, and the lock orders each registration against the publisher’s transition, so no wake-up is lost. Reading a finished value and driving a producer inline create no wake. Raw arrival retains the same wake for claim release and settlement; all three transitions notify only after releasing the state lock.
  • HDL-26 (interrupted decoding). A get() driving a producer on Python’s main thread also runs its decoding there, where a signal handler can raise mid-decode. Deferred producers decode through ReceiveOutcome::decode, which takes a decoding failure raised there that is not an Exception, such as KeyboardInterrupt, as the caller’s interrupt, not the outcome. get() raises it and decodes the same input again on Tokio, so the outcome still reaches the core and stays readable. A failure that is an Exception is the outcome, and so is an exception the message itself carries, whatever its type. The retry unpickles from the start: side effects of the interrupted attempt, such as a user __setstate__’s, are not undone.
  • HDL-27 (one raw reconstruction claim). One observer claims a successful raw reply under the state lock, then unpickles outside it. Success or an ordinary Exception stores one shared outcome. An observer-side BaseException, unwind or cancelled GIL wait releases the claim, preserves the original payload and wakes waiters. Asyncio pipe/fallback workers instead settle every reconstruction failure, including BaseException or caught unwind, before delivering a terminal-only completion token. They retain the claim through error settlement; no competitor can claim between unwind and publication.
