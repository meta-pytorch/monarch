Shared TLS-aware reqwest client construction for mesh-admin HTTP clients.

The mesh admin server requires mutual TLS. Building a correct reqwest::Client against it is subtle because fbcode Buck builds compile both native-tls and rustls features into reqwest, and the two backends use incompatible Identity constructors.

This module centralizes that logic so that every mesh-admin client (admin TUI, integration tests, future tooling) shares the same correct code path.

§Transport selection (highest priority first)

  1. --plaintext: plain HTTP, ignoring any TLS material.
  2. Explicit http:// scheme: plain HTTP. Combining it with --tls-ca / --tls-cert / --tls-key is a hard error.
  3. Explicit --tls-ca (with optional --tls-cert + --tls-key for mutual TLS): an unreadable or invalid CA, a cert/key that cannot be read, or only one of cert/key, is a hard error. --tls-cert/--tls-key without --tls-ca is also an error, since they are unusable without a CA.
  4. Auto-detection via hyperactor::channel::try_tls_pem_bundle (OSS config first, then Meta well-known paths).
  5. If no CA is found and TLS is expected (an https:// scheme or, at Meta, the default), that is a hard error; otherwise (OSS with no certs) fall back to plain HTTP.

Transport is fail-closed: when TLS is expected but cannot be configured, build_client returns an error rather than silently downgrading to plain HTTP.
